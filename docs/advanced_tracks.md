# Advanced Tracks — Implementation Evidence

This document claims and documents the advanced tracks implemented in the
Tunisian Student Early-Warning & Well-Being Platform exam project.
Per the specification, at least **two** tracks are required; this project
implements **three full tracks** (A, B, D) and one partial track (F).

---

## Track A — Architecture and Performance

### What was built

A dedicated **service layer** separates all business logic from the HTTP
views. Views are thin adapters that call service functions and render
responses; they contain no scoring, validation, or transaction logic.

A consistent ORM discipline avoids N+1 queries across every list view.

### Evidence

#### Service layer — `cases/services.py`

| Function | Line | Purpose |
|---|---|---|
| `ingest_sers_csv()` | 48 | Parses, validates, scores, and persists an entire CSV batch inside a single `transaction.atomic()` block. Bad rows are caught, reported, and the whole batch is rolled back via a `_Rollback` sentinel (line 155). |
| `create_followup_reminder()` | 172 | Logs an automatic `CaseEvent(REMINDER)` for overdue intervention plans. Called by the scheduler / seed command, not from any view. |
| `_Rollback` sentinel | 164 | Internal exception class that triggers the atomic rollback without exposing it as a public API. |

The separation means the entire scoring + ingestion pipeline can be tested
without spinning up HTTP:

```python
# cases/tests/test_csv_ingestion.py  — no client, no request object
result = ingest_sers_csv(io.BytesIO(csv_bytes), operator=op)
assert result.created == 1
```

#### ORM — avoiding N+1 queries

| Location | Line | Technique |
|---|---|---|
| `_scoped_entries()` | `cases/views.py:35` | `select_related("student", "operator")` pre-fetches both FK targets in one SQL JOIN |
| `case_detail()` | `cases/views.py:77` | `select_related("student", "operator")` on the full queryset |
| `case_detail()` events | `cases/views.py:101` | `select_related("actor")` on the audit trail queryset |
| `case_detail()` plans | `cases/views.py:102` | `select_related("assigned_to")` on intervention plans |
| `SERSEntry.compute_sers()` | `cases/models.py:255` | Accepts a `policy` object; the caller fetches `SERSPolicy.current()` once and passes it in, avoiding a repeated DB hit inside a loop |

## Track B — Security and Privacy by Design

### What was built

Role-based access control (RBAC) is enforced at three levels:

1. **Decorator layer** — `role_required()` blocks wrong-role users before
   any view logic runs.
2. **Queryset scoping** — Operators can only see entries for their own school.
3. **Audit logging** — every denied or suspicious action is written as an
   immutable `CaseEvent` row.

### Evidence

#### `role_required()` decorator — `accounts/permissions.py:22`

```python
def role_required(*roles: str) -> Callable:
    allowed: set[str] = {Role(r).value for r in roles}

    def decorator(view_func):
        @wraps(view_func)
        @login_required
        def _wrapped(request, *args, **kwargs):
            if getattr(user, "role", None) not in allowed:
                raise PermissionDenied(...)   # → HTTP 403
            return view_func(request, *args, **kwargs)
```

Used on every sensitive view, e.g.:

| View | Guard |
|---|---|
| `sers_policy_edit` | `@role_required(Role.ADMIN)` |
| `case_transition` | `@role_required(Role.SUPERVISOR, Role.ADMIN)` |
| `entry_create` | `@role_required(Role.OPERATOR, Role.ADMIN)` |

#### Operator scoping — `cases/views.py:33–42`

```python
def _scoped_entries(user):
    qs = SERSEntry.objects.select_related("student", "operator")
    if user.is_program_admin or user.is_supervisor:
        return qs                              # full access
    if user.is_operator:
        base = qs.filter(operator=user)
        if user.school:
            base = (base | qs.filter(student__school=user.school)).distinct()
        return base
    return qs.none()
```

#### Audit logging — `cases/views.py:88–95`

When an Operator tries to access a case outside their school, the view
logs a `CaseEvent(action=SECURITY)` before raising `PermissionDenied`:

```python
CaseEvent.objects.create(
    entry=entry, actor=request.user,
    action=CaseEvent.Action.SECURITY,          # line 89
    detail=f"Operator {request.user.username} attempted to view ..."
)
raise PermissionDenied("You may not access this case.")  # line 95
```

`CaseEvent` rows are immutable (no `update` path; `created_at` uses
`default=timezone.now, editable=False`).

#### Synthetic data

All student records are generated by `Faker` in
`accounts/management/commands/seed_demo_data.py`.
No real student data is stored anywhere in this repository.

## Track D — Observability and Reliability

### What was built

Every HTTP request carries a unique correlation ID that flows through
structured log records, the response header, and can be used to trace a
full request/response cycle in the logs.

CSV uploads are atomic — any bad row rolls back the entire batch.

The KPI dashboard provides three reliability proxy metrics.

### Evidence

#### `RequestCorrelationMiddleware` — `wellbeing/middleware.py:32`

```python
class RequestCorrelationMiddleware:
    header = "HTTP_X_CORRELATION_ID"

    def __call__(self, request):
        cid = request.META.get(self.header) or str(uuid.uuid4())
        token = _correlation_id.set(cid)          # stored in ContextVar
        try:
            response = self.get_response(request)
        finally:
            _correlation_id.reset(token)
        response["X-Correlation-ID"] = cid         # line 47 — echoed back
        return response
```

The `CorrelationFilter` (`wellbeing/middleware.py:26`) attaches
`correlation_id` to every `logging.LogRecord`, so the structured format:

```
%(asctime)s level=%(levelname)s correlation_id=%(correlation_id)s logger=%(name)s %(message)s
```

produces output like:

```
2025-11-01 09:12:03,441 level=WARNING correlation_id=3fa2c1d0-… logger=wellbeing.cases
CSV row 7 rejected: Must be between 1 and 10.
```

Every log line for a single request shares the same `correlation_id`,
making it trivial to reconstruct a full request trace.

#### Atomic CSV upload — `cases/services.py:91–160`

```python
with transaction.atomic():          # line 91
    for i, row in enumerate(reader, start=2):
        try:
            entry.save()            # line 133
            result.created += 1
        except Exception as exc:
            result.errors.append(…)
            result.skipped += 1     # line 150
    if result.has_errors:
        raise _Rollback()           # line 155 → rolls back everything
except _Rollback:
    result.created = 0              # line 160 — caller sees truthful count
```

A single bad row in a 100-row file leaves the database unchanged.

| Validation pass rate | `intakes / (intakes + denied) × 100` | 37 |
| Intervention completion rate | `plan_completed / plan_total × 100` | 53 |
| Security event count | `CaseEvent.filter(action=SECURITY).count()` | 35 |

## Track F — RAG / LLM Extension (Partial)

### What was built

A lightweight keyword-retrieval assistant (`support/rag/`) allows peer
supporters to query WHO/UNICEF psychosocial guidelines without any
external API or opaque model call.

### Evidence

#### `support/rag/retriever.py`

| Function | Line | Purpose |
|---|---|---|
| `load_chunks()` | 16 | Reads `guidelines.txt`, splits on `---` separator, returns a list of stripped text chunks |
| `retrieve(query, top_k=3)` | 27 | Tokenises the query, scores each chunk by distinct word hits (TF-style), returns top-k non-zero-score chunks |

No external API key, no network call, no black-box embedding model.

#### `support/rag/guidelines.txt`

12 chunks covering: active listening, safe messaging, escalation triggers,
self-help tools, confidentiality, grief support, cultural sensitivity,
resilience, boundaries, trauma-informed care, crisis de-escalation,
session structure.

#### Explainability

- The matched chunks are displayed verbatim in `support/rag_assistant.html`
  with a teal left border — the user sees exactly what the system found.
- A disclaimer card reminds the user that this is general guidance only.
- The Supervisor can dismiss any suggestion; no action is taken automatically.
